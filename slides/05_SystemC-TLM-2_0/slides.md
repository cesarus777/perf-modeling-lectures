# Конец 1990-х: Проблема "Вавилонской башни"

<div class="m-16"/>

- **Контекст**: Расцвет SoC: На одном кристалле — процессор, память, периферия
- **Проблема**: Архитекторы систем использовали разные языки и инструменты, модели были несовместимы
- **Главный вызов**: Нужен единый язык для описания системы на высоком уровне — и для hardware, и для software

# Рождение SystemC: Synopsys + CoWare 

<div class="m-16"/>

- **Инициаторы**: Компании Synopsys и CoWare
- **Идея**: Взять стандартный C++ и добавить к нему библиотеки классов для аппаратного моделирования
- **Сентябрь 1999**: Образован OSCI (Open SystemC Initiative) — открытый консорциум
- **Первые участники**: 40+ компаний — EDA, IP, полупроводники, встраиваемое ПО 

<!--
Ключевое решение, определившее успех, — не изобретать новый язык, а надстроить существующий. Synopsys и CoWare предложили использовать C++ как базис. А чтобы стандарт стал индустриальным, нужна была поддержка сообщества. В сентябре 1999 года 40 ведущих компаний создали OSCI — открытую организацию по развитию SystemC . Это был сигнал рынку: это всерьёз и надолго.
-->

# Ранние версии: от 0.9 к 1.0 (1999-2000)

<div class="m-16"/>

- **1999**: SystemC 0.9 — первая публичная версия PoC (proof-of-concept)
- **2000**: SystemC 1.0 — стабильное ядро, базовая функциональность: модули, порты, процессы, сигналы 
- **Июнь 2000**: Synopsys выпускает SystemC Compiler — возможность синтеза аппаратуры из SystemC

<!--
Развитие шло стремительно. Уже через год после образования консорциума выходит версия 1.0, которая даёт базовые строительные блоки: SC_MODULE, SC_THREAD, порты, сигналы. Но главный прорыв 2000 года — появление компилятора Synopsys, который позволял синтезировать RTL-код из SystemC-описания. Это сломало барьер недоверия со стороны аппаратчиков: теперь на SystemC можно было не только моделировать, но и получать "железо".
-->

# Версия 2.0 и стандартизация (2001-2005)

<div class="m-16"/>

- **Октябрь 2001**: SystemC 2.0 — появление транзакционного моделирования (TLM 1.0), каналов, интерфейсов
- **Декабрь 2005**: SystemC становится стандартом IEEE 1666-2005

<!--
Версия 2.0 стала революционной — в неё заложили концепцию транзакций и каналов высокого уровня. Это позволило подняться над проводами и тактами. А в 2005 году стандарт получил официальный статус IEEE — международное признание. Теперь SystemC стал не просто "игрушкой энтузиастов", а официальным инженерным инструментом.

# Что такое SystemC сегодня

<div class="m-16"/>

- **Это**: Библиотека классов C++ с открытым исходным кодом
- **Ядро**: Событийный симулятор (discrete-event simulation kernel)
- **Ключевые возможности**:
  - Модульность (`SC_MODULE`) — иерархические блоки
  - Параллельные процессы (`SC_THREAD`, `SC_METHOD`)
  - Специальные типы данных (`sc_int<64>`, `sc_logic`, `sc_fixed`)
  - Коммуникационные каналы (сигналы, FIFO, mutex, семофоры)

<!--
Для инженера-программиста SystemC выглядит как привычный C++ с дополнительной библиотекой. Вы подключаете #include <systemc.h>, объявляете класс, наследующий от sc_module, регистрируете потоки (SC_THREAD), и они выполняются параллельно под управлением встроенного симулятора. Добавлены специальные типы — например, sc_int<64> для точного моделирования разрядности или sc_logic для четырёхзначной логики.
-->

# Промышленный контекст: зачем это нужно?

<div class="m-16"/>

- **Статистика** (Synopsys/IBS, 2007): Разработка ПО составляет до 45-62% общих усилий в SoC-проектах
- Wilf Corrigan, LSI Logic, 1999: "Самая насущная потребность — позволить разработчикам ПО начинать верификацию одновременно с разработкой аппаратуры"
- **Решение SystemC/TLM**: Виртуальные прототипы доступны через 4-6 недель после спецификации архитектуры

<!--
Посмотрите на цифры. Исследования Synopsys и IBS в 2007 году показали, что разработка ПО в современных чипах забирает почти половину всех усилий проекта, а в экстремальных случаях — больше 60%. При этом раньше софтверщики сидели и ждали, пока аппаратчики сделают RTL. SystemC с транзакционным моделированием позволяет создать виртуальный прототип за месяц после утверждения архитектуры и отдать его программистам . Это называется "сдвиг разработки ПО влево".
-->

- **Что мы хотим**: Просто сказать: "Я послал пакет данных"

<!--
AXI это пример Ready/Valid протокола. Такой протокол подразумевает handshake, в процессе которого передающий сообщает, что у него готовы валидные данные (VALID), а принимающий сообщает, что он готов принимать новые данные (READY). Без достижения этих условий, передача не происходит.

# Философия TLM: Вызов функции как транзакция

<div class="m-16"/>

::left::

- **Коммуникация == Вызов метода**
- Модуль А (Initiator) вызывает функцию модуля Б (Target)
- Параметры функции = Данные транзакции (адрес, указатель на данные и т.д.)

Initiator (инициатор, тот, кто начинает общение) вызывает метод у Target (цель, тот, кто обслуживает). Вход и выход из метода и есть начало и конец транзакции. # Ключевой принцип: Разделение вычислений и коммуникации

<div class="m-16"/>

::left::

**Вычисления (что делаем)**: Остаются внутри модулей

**Коммуникация (как общаемся)**: Выносится в интерфейсы (каналы/сокеты)

Модель фокусируется на коммуникации между процессами, а не на алгоритмах внутри них

# Что дает такой подход?

<div class="m-16"/>

1. **Скорость**: Отказ от симуляции каждого такта
1. **Гибкость**: Легко менять "топологию" системы (переподключать модули)
1. **Ранняя разработка ПО**: Драйверы и ОС можно запускать на TLM-модели до появления RTL
1. **Стандартизация**: Модели от разных vendors (ARM, Synopsys) могут работать вместе

<!--
Вместо миллионов тактов мы получаем несколько вызовов функций. Это дает ускорение в тысячи раз. И, что критически важно для индустрии, это позволяет начать разработку программного обеспечения (прошивок, драйверов, ОС) за многие месяцы до получения первого кремния. А стандартизация (IEEE 1666) гарантирует, что модель процессора от ARM сможет работать с моделью контроллера прерываний от другой компании.
-->

# TLM 1.0: Первая ласточка

<div class="m-16"/>

- **Год рождения**: 2005, OSCI (Open SystemC Initiative)
- **Главная идея**: Доказать, что транзакционное моделирование вообще работает
- **Механизм**: Классическое ООП наследование интерфейсов в C++
- **Новшество**: Появление `sc_export` — возможность "выставить" интерфейс дочернего модуля наружу

<!--
В середине 2000-х индустрия осознала: RTL-симуляция целых SoC неподъемна. Нужен способ общаться на высоком уровне.

TLM 1.0 стал первым стандартизированным ответом . Он использовал привычные для C++ программистов механизмы — наследование классов. Если модуль хотел говорить на каком-то протоколе, он просто наследовал соответствующий интерфейс.

Критически важным было появление sc_export. Представьте: у вас сложный модуль (например, процессорное ядро с кэшем). Сам процессор — это инициатор, а кэш — целевое устройство для памяти. Нам нужно, чтобы внешний мир видел интерфейс кэша. sc_export позволяет "пробросить" интерфейс от внутреннего компонента наружу, не делая его полноправным портом верхнего уровня.

В объектно-ориентированной модели SystemC модуль (SC_MODULE), который хотел предоставить другим модулям некоторый сервис (интерфейс), должен был этот интерфейс реализовать. Это делалось с помощью множественного наследования C++: модуль наследовался от класса нужного интерфейса .

Пример: Модуль Processor наследуется от интерфейса memory_if и реализует его методы. Другой модуль может подключиться к нему через sc_port.

Проблема возникала, когда модуль был составным. Представьте себе сложную систему на кристалле (SoC), собранную в корневом модуле Chip. Внутри Chip есть модуль MemoryController, который на самом деле и является "владельцем" интерфейса памяти. Сам Chip не реализует этот интерфейс. Как сделать так, чтобы внешний мир мог подключиться к Chip и через него получить доступ к памяти внутри MemoryController?

До появления sc_export это было сделать крайне сложно или невозможно, так как интерфейс должен был быть реализован именно тем модулем, который его экспортирует.

sc_export действует как "прокси" или "шлюз" . Он позволяет модулю верхнего уровня объявить, что он предоставляет определенный интерфейс, но при этом "перенаправить" вызовы методов этого интерфейса внутрь себя, к конкретному дочернему модулю, который этот интерфейс реально реализует
-->

# TLM 1.0: Болевые точки

<div class="m-16"/>

- **Зоопарк форматов полезной нагрузки (Payload)**: Нет стандартного формата транзакции
- **Забытое время**: Не было встроенного механизма аннотации задержек
- **Проблема множественных портов**: Сложно сделать маршрутизатор с 16 портами, реализующими одинаковый интерфейс

<!--
- TLM 1.0 дал синтаксис, но не дал семантики. Вы могли сделать вызов метода write(), но что передавать в этом методе? Адрес и данные в виде сырых указателей? А как быть с байтовыми масками? Каждый разработчик изобретал свой велосипед .
- Хуже того, TLM 1.0 никак не регламентировал время. Выходило, что транзакция происходит мгновенно. Для функционального моделирования ПО это иногда сойдет, но для performance-анализа — бесполезно.
- И чисто техническая проблема C++: если вам нужно 16 портов с одинаковым интерфейсом, вам приходилось создавать 16 разных классов-наследников или использовать шаблонные "костыли". Для аппаратуры это нонсенс — у маршрутизатора действительно 16 одинаковых портов 
-->

# TLM 2.0

<div class="m-16"/>

- **Год рождения**: Июль 2008
- **Ключевая мотивация**: Совместимость моделей от разынх вендоров (чтобы модель CPU от ARM и модель памяти от Synopsys могли работать вместе "из коробки")
- **Статус**: Вошел в IEEE Standard 1666-2011 (официальная стандартизация)

**TLM 1.0** представил **концепцияю**, **TLM 2.0** привнес **стандартизацию коммуникации**

<!--
- К 2008 году стало ясно: чтобы виртуальные прототипы стали массовым продуктом, нужен единый язык общения. Нельзя требовать от инженера ARM знать, как именно инженер из Synopsys назвал поля своей транзакции .
- OSCI (ныне Accellera) проделала гигантскую работу, проанализировав лучшие практики индустрии, и выпустила TLM 2.0. Это была не просто заплатка, а переосмысление стандарта.
- В 2011 году TLM 2.0 официально стал частью IEEE стандарта 1666™, получив статус не просто "библиотеки от OSCI", а международно признанного стандарта 
-->

# Проблема: Сложность множественных интерфейсов

<div class="m-16"/>

В TLM 1.0: нужно вручную управлять `sc_port` (для вызовов наружу) и `sc_export` (для обработки вызовов извне)

Для двустороннего общения требовалось объявлять и связывать их по отдельности

<!--
В TLM 1.0, если модуль хотел инициировать транзакции и отвечать на них, нужно было возиться с двумя разными механизмами — портами и экспортами — и соединять их отдельно. Для простого маршрутизатора с 16 портами это превращалось в кошмар.
-->

---

# Решение: Сокеты как "два в одном"

<div class="m-16"/>

- **Сокет** — это объект, объединяющий **порт** и **экспорт** в одном флаконе.
- **Initiator socket**: для модулей, которые начинают общение.
- **Target socket**: для модулей, которые отвечают.
- Один вызов `bind()` соединяет сразу оба направления коммуникации 

<!--
Сокеты — это элегантное инженерное решение. Они прячут внутри себя всю сложность организации двусторонней связи. Представьте, что вам не нужно отдельно подключать микрофон и наушники — у вас один USB-разъём, который делает всё сразу. Вот что такое сокет в TLM 2.0
-->

---

# Примеры кода

<div class="m-16"/>

```cpp
// В модуле-инициаторе
tlm_utils::simple_initiator_socket<Initiator> socket;

// В модуле-цели
tlm_utils::simple_target_socket<Memory> socket;

// В топ-уровне: соединение одной строкой
initiator->socket.bind( memory->socket );

// Важно: сокеты можно объявлять массивами!
tlm_utils::simple_target_socket<Router> target_sockets[16];
```

<!--
Обратите внимание на шаблонный параметр — имя модуля-владельца. Это позволяет сокетам автоматически находить нужные методы обратного вызова. simple_initiator_socket и simple_target_socket — это готовые "удобные" сокеты из библиотеки tlm_utils, которые скрывают 90% шаблонного кода . А вызов bind() делает всю магию соединения за нас.

Помните проблему TLM 1.0 с множественными портами? В TLM 2.0 она решена. Для маршрутизатора или шины мы можем объявить массив сокетов одного типа. Это идеально соответствует аппаратной реальности — у устройства действительно может быть 16 одинаковых slave-портов.
-->

# Решение: tlm_generic_payload

<div class="m-16"/>

- Стандартизированный набор полей для memory-mapped транзакций.
- Поля Generic Payoload (GP):
  - `command`: `TLM_READ_COMMAND` / `TLM_WRITE_COMMAND`
  - `address`: 64-битный адрес
  - `data_ptr`: указатель на буфер с данными
  - `data_length`: размер данных в байтах
  - `streaming_width`: для потоковых операций
  - `byte_enable_ptr`: байтовые маски (для частичных записей)
  - `response_status`: `TLM_OK_RESPONSE`, `TLM_INCOMPLETE_RESPONSE` и др.


<!--
Generic Payload — это стандартный конверт для передачи данных. Любая TLM-2.0 модель гарантированно понимает структуру этого конверта. Даже если внутри у неё своя логика, поля адреса, команды и данных будут всегда на своих местах.
-->

---

# Пример использования GP в коде

<div class="m-16"/>

```cpp
tlm::tlm_generic_payload trans;
trans.set_command(tlm::TLM_WRITE_COMMAND);
trans.set_address(0x1000);
trans.set_data_ptr(reinterpret_cast<unsigned char*>(&data));
trans.set_data_length(4);
trans.set_streaming_width(4);
trans.set_byte_enable_ptr(0); // null = все байты активны
trans.set_response_status(tlm::TLM_INCOMPLETE_RESPONSE);
```

<!--
Вот так выглядит подготовка транзакции. Методы set_* делают код читаемым и понятным. Обратите внимание на streaming_width — эта поле нужно для burst-операций, где длина данных может не совпадать с шириной шины. А byte_enable_ptr позволяет делать запись только в определённые байты по указанному адресу.

Generic Payload не управляет памятью автоматически. Если инициатор создал транзакцию через new, он же должен вызвать delete после получения ответа. Иначе — утечки. В промышленных моделях часто используют пулы транзакций для переиспользования объектов и избегания накладных расходов на выделение памяти.
-->

# Временная аннотация

<div class="m-16"/>

Если мы убрали такты, как узнать, сколько времени заняла операция?

<div class="m-8"/>

Ответ: Время явно передаётся как дополнительный аргумент — `sc_time &delay`

<!--
В TLM мы не моделируем каждый такт, но мы должны моделировать время, иначе мы не сможем анализировать производительность. Решение гениально в своей простоте: время "пристёгивается" к транзакции в виде дополнительного параметра. Модель памяти говорит: "Я обработаю этот запрос, но это займёт 100 наносекунд"
-->

# Два стиля временной аннотации

<div class="m-16"/>

::left::

### Loosely-Timed (LT)

<div class="m-6"/>

- Время квантуется большими "кусками"
- Использует блокирующие вызовы
- Цель: максимальная скорость для загрузки ПО

::right::

### Approximately-Timed (AT)

<div class="m-6"/>

- Транзакция разбивается на фазы (`BEGIN_REQ`, `END_REQ`, `BEGIN_RESP`, `END_RESP`).
- Использует неблокирующие вызовы
- Цель: точный анализ конфликтов и конвейеризации

<!--
TLM 2.0 даёт два уровня точности на выбор. LT — это когда мы хотим быстро запустить драйвер или ОС на виртуальном прототипе, нам важна функциональность, а временные задержки могут быть приблизительными. AT — это когда мы исследуем архитектуру и хотим понять, будут ли конфликты на шине, не переполнятся ли буферы — здесь нужно моделировать фазы транзакции.
-->

---

# LT vs AT: аналогия для программистов

<div class="m-16"/>

**Loosely-Timed (LT)**:
- Вызов удалённой процедуры (RPC)
- Отправили запрос — получили ответ
- Время — это общая длительность вызова.

<div class="m-8"/>

**Approximately-Timed (AT)**:
- Отслеживание пакета в сети
- Пакет проходит через разные узлы, мы видим каждый этап его пути

<!--
Для разработчиков ПО это очень понятная аналогия. LT похож на вызов функции по сети: вы вызвали, подождали и получили результат. А AT — это как смотреть на путь каждого сетевого пакета: вот он отправлен, вот пришёл на маршрутизатор, вот пошёл дальше... Если вы моделируете Network-on-Chip, вам нужен AT. Если вы грузите Linux — вам нужен LT.
-->

---

# Пример LT-вызова в коде

<div class="m-16"/>

```cpp
sc_time delay = SC_ZERO_TIME;
tlm::tlm_generic_payload trans;
// ... заполнение транзакции ...

socket->b_transport(trans, delay); // b_ означает blocking
// После возврата из b_transport, delay содержит
// полное время обработки транзакции
```

<!--
Посмотрите, как это просто. Мы создаём переменную delay (изначально ноль), вызываем b_transport, и модель-цель внутри себя прибавляет к этой переменной нужную задержку. Когда управление вернулось, в delay — суммарное время операции. Ядро SystemC затем прибавит это время к глобальному счётчику симуляции.
-->

---

# Резюме о временной аннотации

<div class="m-16"/>

- **Ключевая идея**: Время — это атрибут **транзакции**, а не тактовый сигнал
- **LT**: `b_transport` + один временной отпечаток — для скорости и загрузки ПО
- **AT**: `nb_transport` + фазы — для точного performance-анализа
- Выбор — всегда компромисс между **скоростью** и **точностью**

<!--
Запомните главное: TLM позволяет моделировать время, не моделируя такты. А выбор между LT и AT — это всегда инженерный компромисс. Хотите быстро прогнать миллиарды инструкций ОС — берите LT. Хотите понять, почему падает пропускная способность в конкретном узле — берите AT.
-->

# Задача: моделируем память (SRAM)

<div class="m-16"/>

**Что делаем**: Простейшая модель памяти, которая хранит данные и отвечает на запросы.

<div class="m-8"/>

**Требования**:
- Принимает запросы чтения/записи
- Хранит данные в массиве
- Возвращает статус выполнения

<!--
Самая простая модель, с которой можно начать — это память. Она ничего не делает, кроме хранения данных, но на её примере виден весь каркас TLM-модели. Это наш "Hello, World!" в мире TLM.
-->

---

# Каркас модуля

<div class="m-16"/>

```cpp
#include "tlm.h"
#include "tlm_utils/simple_target_socket.h"

class Memory : public sc_core::sc_module {
public:
    // 1. Объявляем target-сокет
    tlm_utils::simple_target_socket<Memory> socket;

    Memory(sc_core::sc_module_name name, unsigned int size);

private:
    // 2. Главный метод обработки транзакций
    void b_transport(tlm::tlm_generic_payload& trans, sc_time& delay);

    unsigned char* mem;  // указатель на память
    unsigned int mem_size;
};
```

<!--
Обратите внимание на три ключевые строки. Первая — включение заголовков TLM. Вторая — объявление сокета. Третья — метод b_transport, который будет вызываться, когда кто-то пошлёт транзакцию этому модулю . Шаблонный параметр Memory — это имя нашего класса, он нужен для автоматической привязки методов.
-->

---

# Конструктор и инициализация

<div class="m-16"/>

```cpp
Memory::Memory(sc_module_name name, unsigned int size)
    : sc_module(name), mem_size(size)
{
    // Регистрируем функцию обработки
    socket.register_b_transport(this, &Memory::b_transport);

    // Выделяем память
    mem = new unsigned char[size];
    memset(mem, 0, size);
}

Memory::~Memory() {
    delete[] mem;
}
```

<!--
В конструкторе происходит важная магия — мы регистрируем метод b_transport в сокете. Теперь, когда кто-то вызовет socket->b_transport(), управление придёт именно сюда. Это пример того, как simple_target_socket скрывает от нас сложность наследования интерфейсов.
-->

---

# Реализация `b_transport` (ядро модели)

```cpp
void Memory::b_transport(tlm_generic_payload& trans, sc_time& delay)
{
    tlm_command cmd = trans.get_command();
    uint64 addr = trans.get_address();
    unsigned char* data_ptr = trans.get_data_ptr();
    unsigned int data_len = trans.get_data_length();
    // Проверка адреса
    if (addr + data_len > mem_size) {
        trans.set_response_status(TLM_ADDRESS_ERROR_RESPONSE);
        return;
    }
    // Выполнение операции
    if (cmd == TLM_WRITE_COMMAND) {
        memcpy(&mem[addr], data_ptr, data_len);
    } else if (cmd == TLM_READ_COMMAND) {
        memcpy(data_ptr, &mem[addr], data_len);
    }
    // Успех!
    trans.set_response_status(TLM_OK_RESPONSE);
    // Добавляем задержку (пока фиксированную)
    delay = delay + sc_time(10, SC_NS);
}
```

<!--
Это сердце модели. Мы получаем транзакцию, извлекаем из неё команду, адрес, данные. Проверяем, не выходит ли адрес за пределы памяти. Выполняем операцию. Возвращаем статус. И, самое главное, добавляем время к параметру delay. Обратите внимание — мы не вызываем wait(), мы просто увеличиваем переменную.
-->

---

# Важное наблюдение

<div class="m-16"/>

- Модель не содержит ни одного `wait()` в этом методе!
- Вся задержка передаётся через параметр `delay`
- Ядро SystemC само приостановит симуляцию на это время после возврата из `b_transport`

<div class="m-16"/>

Схема: Initiator -> вызов `b_transport` -> Target (обработка) -> <br> &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; -> возврат -> ядро ждёт `delay` -> продолжение

# Проблема: что если устройство занято?

::left::

<div class="m-16"/>

- В реальном мире устройства не могут обрабатывать запросы мгновенно
- Если запрос приходит, а устройство ещё занято предыдущим — запрос становится в очередь
- Это называется **back-pressure** (обратное давление)

::right::

<div class="flex items-center justify-center h-full w-full">
  <div class="w-90%">
    <img src="/queue.jpg" class="w-full">
  </div>
</div>

<!--
Наша простая модель памяти обрабатывает запросы мгновенно (ну, почти — мы добавили задержку, но она обрабатывает их один за другим без очереди). Если два запроса придут одновременно, второй будет ждать завершения первого, но он не становится в очередь — он просто блокирует инициатора. А если мы хотим моделировать конвейерное устройство или устройство с очередью?
-->

---

# Решение: добавляем очередь и SC_THREAD

<div class="m-16"/>

```cpp
class QueuedMemory : public sc_module {
public:
    tlm_utils::simple_target_socket<QueuedMemory> socket;

    SC_HAS_PROCESS(QueuedMemory);
    QueuedMemory(sc_module_name name, int queue_size);

private:
    void b_transport(tlm_generic_payload& trans, sc_time& delay);
    void process_queue();  // SC_THREAD

    tlm_utils::peq_with_get<tlm_generic_payload> request_queue;  // очередь
    bool busy;
};
```

<!--
Мы вводим два новых элемента. Первый — peq_with_get (Payload Event Queue) — специальная очередь из библиотеки TLM, предназначенная для хранения транзакций . Второй — SC_THREAD process_queue, который будет забирать транзакции из очереди и обрабатывать их.
-->

---

# Реализация `b_transport` с очередью

<div class="m-16"/>

```cpp
void QueuedMemory::b_transport(tlm_generic_payload& trans, sc_time& delay)
{
    if (busy) {
        // Если устройство занято, ставим в очередь
        request_queue.notify(trans, delay);
        // Мы не можем вернуть управление сразу, надо подождать
        wait(busy_event);
    }

    // Устройство свободно, начинаем обработку
    busy = true;
    // Запускаем процесс обработки
    process_thread();
    // Передаём транзакцию в обработчик
    request_queue.notify(trans, delay);
}
```

<!--
Логика меняется. Если устройство занято, мы не можем ответить сразу. Мы ставим транзакцию в очередь и вызываем wait(busy_event), чтобы заснуть до освобождения устройства. Когда устройство освободится, событие busy_event разбудит нас.
-->

---

# Процесс обработки очереди

```cpp
void QueuedMemory::process_queue()
{
    while (true) {
        // Ждём появления транзакции в очереди
        tlm_generic_payload* trans = request_queue.get_next_transaction();
        sc_time delay = request_queue.get_current_time();

        // Обрабатываем транзакцию
        // ... (код обработки из предыдущего примера)

        // Симулируем время обработки
        wait(processing_time);

        // Освобождаем устройство и будим ожидающих
        busy = false;
        busy_event.notify();
    }
}
```

Initiator1 -> `b_transport` (занято -> в очередь) -> Initiator2 -> `b_transport` (занято -> в очередь) -> `process_queue` достаёт из очереди -> обрабатывает -> `busy_event.notify()`

<!--
Теперь у нас полноценная модель с очередью. peq_with_get хранит транзакции и время их поступления. Процесс process_queue работает в бесконечном цикле, забирает транзакции из очереди, обрабатывает их с реальной задержкой (через wait(processing_time)) и сигнализирует об освобождении. Это уже модель, способная создавать back-pressure.
-->

---

# Задача: несколько инициаторов, один ресурс

<div class="m-16"/>

- Несколько процессоров хотят обращаться к одной памяти
- Нужен арбитр, который решает, кто получит доступ
- Арбитр должен быть "прозрачным" — перенаправлять транзакции, но учитывать задержки арбитража

<!--

# Каркас арбитра с массивами сокетов

template<int N_INITIATORS, int N_TARGETS>
class SimpleBus : public sc_module {
public:

# Реализация `b_transport` и арбитража

<div class="m-16"/>

```cpp
void SimpleBus::b_transport(int id, tlm_generic_payload& trans, sc_time& delay)
{
    // 1. Декодируем адрес и выбираем целевой порт
    uint64 addr = trans.get_address();
    int target_id = addr >> 32;  // простейшая декодировка: старшие биты — номер устройства

    // 2. Арбитраж (если несколько запросов одновременно)
    // В простейшем случае — первый пришёл, первый обслужен
    // Но если мы хотим моделировать конфликты, нужно добавить очередь
    arbiter_wait(trans, id);  // здесь может быть ожидание

    // 3. Добавляем задержку арбитра
    delay = delay + sc_time(1, SC_NS);

    // 4. Форвардим транзакцию в нужный целевой сокет
    initiator_socket[target_id]->b_transport(trans, delay);

    // 5. Ответ вернётся автоматически через тот же путь
}
```

<!--
Арбитр делает три вещи: декодирует адрес, решает, кто сейчас получит доступ (если несколько запросов висят одновременно), добавляет свою задержку и форвардит транзакцию дальше. Когда целевое устройство вернёт ответ, он автоматически пойдёт обратно по тому же пути.
-->

<div class="m-16"/>

- **Сложный арбитр**: моделирует реальные задержки арбитража

<div class="m-8"/>

# Эскиз модели DRAM-контроллера

```cpp
void DramController::b_transport(tlm_gp& trans, sc_time& delay)
{
    if (trans.get_command() == TLM_WRITE_COMMAND) {
        write_queue.push(trans, delay);
    } else {
        read_queue.push(trans, delay);
    }
    scheduler_thread();  // планировщик проснётся
}

void DramController::scheduler_thread()
{
    while (true) {
        if (can_schedule_read(read_queue.front())) {
            // Активировать банк (tRCD)
            wait(trcd_delay);
            // Прочитать данные (tCAS)
            wait(tcas_delay);
            // Отправить ответ
        }
        // Арбитр между read и write очередями
    }
}
```

<!--
Вот как выглядит типичная промышленная модель DRAM-контроллера. Внутри — конечный автомат, работающий с несколькими очередями. Это всё те же кирпичики: сокеты, generic payload, очереди, SC_THREAD и временные задержки. Просто их комбинация становится сложнее.
-->

# Ключевой вывод

<div class="m-16"/>

Любая **сложная** модель строится из **простых** элементов:
- Сокет для приёма/передачи транзакций
- Очередь для хранения ожидающих запросов
- `SC_THREAD` для обработки очереди
- Внутреннее состояние (память, регистры, FSM)
- Временные аннотации (`wait()` или `delay`)

<!--
Запомните эту схему. Это универсальный шаблон, по которому строятся 90% TLM-моделей. Сокет принимает запрос, если ресурс занят — запрос идёт в очередь, SC_THREAD забирает из очереди, обновляет состояние, добавляет задержку, отправляет ответ. Меняется только внутренняя логика обработки, а каркас остаётся тем же.
-->
